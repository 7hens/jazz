# 个人项目需求版本管理规范

> **版本**：3.2
> **适用场景**：单人开发 | 快速迭代 | 需求多变
> **配套文档**：`docs/RELEASE.md`（发布操作手册）

## 0. 文件目录总览

```
项目根目录/
├── CHANGELOG.md              # 📜 历史记录（根目录，符合 Keep a Changelog 规范）
├── docs/
│   ├── RELEASE.md            # 🚀 发布操作手册（只有一份，含自测点检）
│   ├── IDEAS.md              # 💡 需求池 / 停车场（原始想法）
│   ├── BACKLOG.md            # 📋 待办池 / 等车棚（已规划待排期）
│   ├── TODO.md               # 📌 当前看板 / 发车台（当前迭代）
│   └── features/             # 📄 详细需求文档库（每个需求一个 .md 文件）
│       ├── template.md       # 新建需求时复制的模板
│       ├── dark-mode.md      # 示例：深色模式需求
│       └── excel-export.md   # 示例：导出 Excel 需求
├── migrations/               # 🗄️ 数据库迁移（按数字前缀，与版本无关）
│   ├── 0001_init.sql
│   └── 0002_add_status.sql
└── src/                      # 源代码
```

**设计原则**：每个需求只用一个 `.md` 文件描述。如果一个需求复杂到需要多个文件才能说清，说明它应该被拆解为多个独立需求。

## 1. 核心理念

需求管理的本质不是“管住需求”，而是**管住自己**。每一个新需求都是一次“诱惑”，规范的目的是帮你在诱惑面前保持清醒，聚焦在最重要的事情上。

**核心公式**：版本号的变更幅度 = 需求的**影响面**，而非工作量。

## 2. 需求四层流转模型

需求从灵感到上线，经历四个阶段，对应四个文件：

```
┌─────────────────────────────────────────────────────────────────┐
│                        需求生命周期                            │
└─────────────────────────────────────────────────────────────────┘

  💡 灵感闪现（任何时间、任何地点）
       │
       ▼
  ┌─────────────┐
  │ IDEAS.md    │  ← 粗略想法，未经评估（停车场）
  │             │    规则：先扔进来，不承诺，不限量
  └─────────────┘
       │
       │ 经过评估（满足准入标准，确认要做）
       ▼
  ┌─────────────┐
  │ BACKLOG.md  │  ← 已规划、已确认、待排期（等车棚）
  │             │    规则：只放标题 + 链接，详细文档在 features/xxx.md
  └─────────────┘
       │
       │ 发版日/复盘后，决定排入下个迭代
       ▼
  ┌─────────────┐
  │ TODO.md     │  ← 当前迭代正在做（发车台）
  │             │    规则：只放当前迭代内容，每天更新进度
  └─────────────┘
       │
       │ 发版日：按 RELEASE.md 执行部署，冒烟测试通过
       ▼
  ┌─────────────┐
  │ CHANGELOG.md│  ← 已上线，成为历史记录（行程记录）
  │             │    规则：只追加，不修改
  └─────────────┘
```

## 3. 文件职责详解

### 3.1 `docs/IDEAS.md`（需求池 / 停车场）

**职责**：收集所有原始想法，不管成熟与否，先记下来防止遗忘。

**模板**：

```markdown
# 需求池（IDEAS）

> 最后更新：2026-09-04
> 规则：任何想法先入池，禁止直接开工

## 待评估（按感觉优先级排序）
- [ ] 深色模式 — 夜间使用刺眼，已有多人反馈
- [ ] 导出 Excel 报表 — 用户群有人问过
- [ ] 接入 AI 总结 — 感觉会很酷
- [ ] 登录页倒计时优化 — 每次看时间都不准

## 已拒绝（记录原因，防止反复纠结）
- [x] 接入微信登录 — 个人主体无法申请（2026-08-20）

## 待观察（暂不排期，值得关注）
- [ ] AI 智能总结 — 等 OpenAI 降价后再评估
```

**准入标准（从 IDEAS → BACKLOG）**：满足以下条件之一即可入 `BACKLOG.md`：

- 用户明确反馈（至少 2 个不同用户，或同 1 用户提了 3 次以上）
- 自己日常使用中至少遇到 3 次痛点
- 技术债务必须还（否则后续开发被阻塞）

**容量限制**：超过 20 条时，强制删除一半（优先删“感觉酷但不实用”的）。

### 3.2 `docs/BACKLOG.md`（待办需求池 / 等车棚）

**职责**：存放已评估、确认要做、但尚未排期的需求。**只放标题 + 链接**，详细文档在 `features/xxx.md`。

**优先级判定规则**：

| 优先级 | 判定标准（满足其一即可） |
| :--- | :--- |
| **高** | 用户明确抱怨（≥ 2 人）/ 阻塞后续开发（技术债）/ 核心流程体验严重受损 |
| **中** | 自己使用中遇到 ≥ 3 次痛点 / 能显著提升效率（非核心功能） |
| **低** | “感觉会很酷” / 竞品有但自己不确定要不要 / 未来技术储备 |

**模板**：

```markdown
# 待办需求池（BACKLOG）

> 说明：已评估确认要做，但未排入具体迭代
> 排期决策：每月复盘或发版日后的规划会议

## 高优先级（计划下 1~2 个迭代内启动）

| 需求 | 级别 | 详细文档 | 备注 | 评估日期 |
| :--- | :--- | :--- | :--- | :--- |
| 深色模式 | L（已拆为 3 个 M） | [spec](./features/dark-mode.md) | 需先调研 CSS 变量方案 | 2026-09-01 |
| 导出 Excel | M | [spec](./features/excel-export.md) | 用户群 5 人反馈需要 | 2026-08-28 |

## 中优先级（计划 1~2 个月内启动）

| 需求 | 级别 | 详细文档 | 备注 | 评估日期 |
| :--- | :--- | :--- | :--- | :--- |
| 接入 AI 总结 | L（需拆解） | [spec](./features/ai-summary.md) | 等 API 降价 | 2026-08-20 |

## 低优先级（暂不排期，保留）

| 需求 | 级别 | 详细文档 | 备注 | 评估日期 |
| :--- | :--- | :--- | :--- | :--- |
| 桌面端打包 | L | [spec](./features/desktop-app.md) | 用户量突破 1000 再考虑 | 2026-06-01 |

## 已移除（不再考虑）

| 需求 | 移除原因 | 移除日期 |
| :--- | :--- | :--- |
| 接入支付宝 | 个人项目暂不涉及支付 | 2026-09-01 |
```

### 3.3 `docs/TODO.md`（当前迭代看板 / 发车台）

**职责**：存放**当前迭代**正在做的需求，每天更新进度。

**关键原则**：

- `TODO.md` **只有一份**，不按版本拆分。
- 发版完成后清空并重新填充下个迭代的内容。

**模板**：

```markdown
# 当前迭代

> 迭代目标：v1.3.0
> 发版日：2026-09-15
> 状态：开发中（第 3/5 天）

## 本次迭代需求

| 需求 | 级别 | 关联文档 | 状态 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 导出 Excel 报表 | M | [spec](../features/excel-export.md) | ✅ 已完成 | — |
| 增加搜索框 | M | [spec](../features/search-box.md) | 🔄 进行中 | 预计明天完成 |
| 修复登录超时跳转 | S | — | ✅ 已完成 | — |

## 发版日行动清单
- [ ] **执行 `docs/RELEASE.md` 完整发版流程**（按顺序逐项完成）
- [ ] 发布后在 `CHANGELOG.md` 中追加记录
- [ ] 本次 `TODO.md` 已完成内容 → 剪切到 `CHANGELOG.md`
- [ ] 从 `BACKLOG.md` 拉取下个迭代需求，填充 `TODO.md`

## 下个迭代候选（v1.4.0）
- 深色模式 — M1（CSS 变量重构）
```

**更新规则**：

- **每天开始编码前**：花 2 分钟看一眼今日任务。
- **每天结束编码后**：花 2 分钟更新状态（完成打 ✅，阻塞写备注）。
- **发版完成后**：把完成的内容剪切到 `CHANGELOG.md`，然后从 `BACKLOG.md` 拉取下个迭代的需求填进来。

### 3.4 `docs/features/`（详细需求文档库）

**职责**：存放每个需求的详细规格说明。

**规则**：

- 每个需求**只用一个 `.md` 文件**描述。
- 如果一个需求复杂到需要多个文件才能说清，说明它应该被**拆解为多个独立需求**。

**目录结构**：

```
docs/features/
├── template.md          # 新建需求时复制的模板
├── dark-mode.md         # 深色模式需求
├── excel-export.md      # 导出 Excel 需求
└── search-box.md        # 搜索框需求
```

**需求文档模板（`features/template.md`）**：

```markdown
# [需求名称]

> 创建日期：YYYY-MM-DD
> 状态：草稿 / 已规划 / 开发中 / 已上线
> 关联版本：vX.X.X（上线后填写）

## 1. 背景与动机
（为什么做？用户反馈了什么？遇到了什么痛点？）

## 2. 用户故事
（谁，在什么场景下，希望达成什么目的）

## 3. 验收标准（非常重要！）
- [ ] 条件 1：具体可验证的行为
- [ ] 条件 2：具体可验证的行为
- [ ] 条件 3：边界情况处理

## 4. 技术方案要点
（涉及哪些模块、API、数据库变更、第三方依赖）

## 5. 拆解计划（L 级必填）
- M1: xxx（预计 0.5 天）
- M2: xxx（预计 1 天）
- M3: xxx（预计 0.5 天）
```

### 3.5 `/CHANGELOG.md`（历史记录 — 根目录）

**职责**：记录每个版本已上线的功能摘要。

**规则**：

- **只追加，不修改**已发布的版本条目。
- 符合 [Keep a Changelog](https://keepachangelog.com/) 规范，放在**项目根目录**（GitHub/GitLab 会自动识别）。

**模板**：

```markdown
# 更新日志

- 导出 Excel 报表（[spec](./docs/features/excel-export.md)）
- 增加全局搜索框

### 修复

## [1.2.0] - 2026-08-30
### 新增
- 深色模式（[spec](./docs/features/dark-mode.md)）

### 修复
- 修复移动端布局错位
```

## 4. 需求分级与版本号映射

### 4.1 三级估算模型

| 级别 | 工作量 | 判断标准 | 建议发布类型 |
| :--- | :--- | :--- | :--- |
| **S（小）** | ≤ 2 小时 | 改文案、修样式、改配置 | 随最近一次发版 |
| **M（中）** | 1~2 天 | 新增独立页面 / 小功能 / 新接口 | 随 **Minor** 发布 |
| **L（大）** | ≥ 3 天 | 改数据库、重构架构、接入新 SDK | **强制拆解**为多个 M |

**50% 边界规则**：当 M 级任务实际耗时达到预估上限（2 天）且完成度不足 50% 时，**立即停止**，将剩余部分拆分并滚入下个迭代。本次发布的版本只包含已完成的部分。

### 4.2 版本号决策表

| 版本号级别 | 触发条件 | 示例 |
| :--- | :--- | :--- |
| **Patch（X.X.↑）** | 修复 Bug、性能优化、文案样式调整 | 修复支付回调超时 |
| **Minor（X.↑.0）** | 新增向下兼容的功能（页面/接口/字段） | 增加导出 Excel 功能 |
| **Major（↑.0.0）** | **破坏性变更**：删除/重命名 API、修改表结构不可逆、重写本地存储逻辑 | API v1→v2 不兼容 |

> **重要区分**：
>
> - **Major（破坏性变更）**：删除字段、重命名表、修改字段类型（不可自动转换）、删除/重命名 API 路由。
> - **Minor（向下兼容）**：新增表、新增字段（带 `DEFAULT` 或允许 `NULL`）、新增 API 路由。
>
> Major 版本**与工作量无关**，仅由“破坏性变更”触发。花了 5 天加了个大功能（非破坏性）→ 升 Minor；只花了 1 小时删了一个旧接口 → 升 Major。

## 5. 迭代节奏控制（发版列车）

### 5.1 双周发版制

| 时间段 | 活动 | 产出 |
| :--- | :--- | :--- |
| **第 1~3 天** | 编码冲刺，完成本次选中的 M 级需求 | 功能代码 |
| **第 4 天** | 处理 S 级需求 / 自测 / 修 Bug | 修复补丁 |
| **第 5 天** | 部署预览环境验证 + 冒烟测试 | 验证通过 |
| **第 6 天（发版日）** | 按 `RELEASE.md` 部署生产 + 打 Tag + 更新 Changelog | `v1.x.0` 正式发布 |

### 5.2 发版日铁律（不可违反）

| 规则 | 说明 |
| :--- | :--- |
| **准时发车** | 无论完成多少，发版日当天必须发版 |
| **只发已完成的** | 已完成的 M/S 级纳入本次发布 |
| **未完成的延后** | 未完成的 M 级自动滚入下个迭代 |
| **空版本处理** | 如果本次所有 M 级均未完成 → 发版取消，只发 S 级作为 Patch |

### 5.3 S 级发布时机

- **非紧急 S 级**（文案、样式）：攒着，随最近一次发版发布，不单独发版。
- **紧急 S 级**（阻断性 Bug）：走 Hotfix 流程（见第 7 节）。

### 5.4 提前完成后的缓冲期

如果提前完成所有任务，**禁止从 BACKLOG 拉新需求**。缓冲期优先级：

1. 补充单元测试 / 集成测试
2. 完善 README.md / CHANGELOG.md / API 文档
3. 拉长自测时间，增加测试覆盖率
4. 如果以上都做完 → 直接提前发版，进入下个迭代

## 6. 发版前自检（两问）

每次发版前（`wrangler deploy` 之前），回答两个问题：

1. **“这些功能做完后，用户真的会感知到吗？”**
   - 如果用户完全无感知（如纯后端性能优化），考虑并入下一个版本，减少发版频率。

2. **“如果今天不上线，会死人吗？”**
   - 如果不会，按原计划发版；如果会，走 Hotfix 流程。

## 7. 紧急插队（Hotfix）

**触发条件**：

- 线上功能完全不可用（白屏、500 错误）
- 支付 / 登录等核心流程阻断
- 数据丢失或安全漏洞

**流程**：

```bash
# 1. 在 main 分支直接修复
git add . && git commit -m "fix: 修复登录超时问题"

# 2. 立即部署（可跳过预览环境，但必须自测核心流程）
wrangler deploy --env production

# 3. 生产冒烟测试通过后，打 Patch Tag
npm version patch -m "chore(hotfix): v%s"
git push origin main --tags

# 4. 在 CHANGELOG.md 中记录
## [1.2.1] - 2026-09-14（紧急修复）
### 修复
- 修复登录超时跳转失效的问题

# 5. 将根因记录到 IDEAS.md 的"待观察"中
```

## 8. 月度复盘（每月最后一个周五）

**时长**：15~20 分钟

**三个核心问题**：

| 问题 | 目的 |
| :--- | :--- |
| 本月发了几个版本？（Major / Minor / Patch 各多少） | 了解迭代节奏是否稳定 |
| BACKLOG 里新增了多少条、拒绝/移除了多少条？ | 拒绝越多，说明越聚焦 |
| 本月最后悔做的需求是哪个？为什么？ | 识别冲动决策模式，避免再犯 |

**记录方式**：在 `IDEAS.md` 末尾追加复盘记录。

```markdown
## 复盘记录

### 2026-09-30（本月复盘）
- 发版：Minor × 2，Patch × 1
- BACKLOG 新增：3 条，移除：4 条
- 最后悔：做了“导出 Excel”，实际上没人用，浪费 2 天
- 下月改进：新功能上线前，先在用户群问一句“你真的需要吗？”
```

## 9. 快速决策速查表

| 问题 | 答案 |
| :--- | :--- |
| 有个新想法，怎么办？ | 先扔 `IDEAS.md`，冷静一下 |
| 怎么判断要不要做？ | 满足准入标准（用户反馈 ≥2 人 / 自己遇到 ≥3 次 / 必须还的技术债） |
| 确认要做了，放哪里？ | 写详细文档到 `features/xxx.md`，在 `BACKLOG.md` 加一行链接 |
| 如何选入当前迭代？ | 发版日/复盘后，从 BACKLOG 高优先级中选 2~3 个 M 级填进 `TODO.md` |
| 做完一个 M 要马上发版吗？ | 不要，攒到发版日统一发 |
| S 级（≤2h）需求怎么做？ | 非紧急攒着随版本，紧急走 Hotfix |
| L 级（≥3天）需求怎么处理？ | 强制拆解为多个 M，分批上线 |
| 什么情况升 Major？ | **只有**破坏性变更（删字段/表/API，且不可向下兼容） |
| 什么情况升 Minor？ | 新增表/字段（带默认值）、新增 API 路由（向下兼容） |
| 发版日到了但需求没做完？ | 完成多少发多少，未完成的滚入下个迭代 |
| 提前完成所有任务？ | 写测试/写文档/提前自测，禁止拉新需求 |
| 线上紧急故障？ | 立即修，走 Hotfix，发 Patch |
| 多久复盘一次？ | 每月一次，回答 3 个问题 |

## 10. 规范速览图

```
┌───────────────┐
│  IDEAS.md     │ ← 灵感停车场（任何想法先扔进来）
│  （需求池）   │
└───────┬───────┘
        │ 评估通过（满足准入标准）
        ▼
┌───────────────┐
│  BACKLOG.md   │ ← 已规划待排期（标题 + 链接）
│  （待办池）   │   features/*.md 放详细文档
└───────┬───────┘
        │ 排期决策（发版日/复盘后）
        ▼
┌───────────────┐
│  TODO.md      │ ← 当前迭代进行中（每日更新进度）
│  （当前看板） │   关联 features/*.md 详细文档
└───────┬───────┘
        │ 发版日（按 RELEASE.md 执行部署 + 冒烟测试）
        ▼
┌───────────────┐
│  CHANGELOG.md │ ← 已上线归档（只追加，不修改）
│  （历史记录） │   位于项目根目录
└───────────────┘
```

## 总结

这套规范的核心是四个词：**限流、聚焦、准时、复盘**。

| 关键词 | 体现 |
| :--- | :--- |
| **限流** | `IDEAS.md` → `BACKLOG.md` 两层过滤，拦住冲动的想法 |
| **聚焦** | `TODO.md` 只放当前迭代内容，避免多任务切换 |
| **准时** | 发版列车固定双周发版，雷打不动 |
| **复盘** | 每月三问，持续优化自己的决策质量 |

**一个人开发时，最大的成本不是写代码，而是“做不该做的事”。** 这套规范能帮你把精力始终放在真正重要的事情上，让每个版本都有实实在在的产出。
