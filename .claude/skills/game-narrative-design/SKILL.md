# 漫画交互叙事设计(game-narrative-design)

## 定位与原则

叙事 = 把「漫画翻页悬念 + 交互选择」落成可写、可校验的结构。目标产出分支树 + 分镜脚本表 + 1 张状态变量表 + 1 张节奏表;每条分支在进视觉前先过**逻辑校验闸门**,防「有选择但殊途同归」的空洞交互。

**分工**:世界观/角色/对白/伏笔的**创作**在 `game-story-writing`(其故事层闸门先行);本技能负责**结构**(分支、变量、节奏)与**逻辑校验**。上游未定稿就排分支 = 返工。

## 结构产出物(骨架见 `references/templates.md`)

> **上游创作**(世界观圣经、角色档案、对白写法、伏笔) → `game-story-writing`;本技能只管把这些**组织成可校验的结构**。

1. **分支树**(三幕式起承转合):节点标「强制 / 可选 / QTE」,标多结局节点与解锁条件;每个节点必须有去向。
2. **分镜脚本表**(逐行):台词与选项文本照 `game-story-writing/references/script-and-craft.md` §四;**结构侧只补差异点 / 状态挂钩 / 演出钩子**三列。
3. **逐幕演出表**(逐幕):回答「这一幕**怎么演**」—— 功能 / 舞台氛围 / 玩家交互 / 转场 / 演出钩子。
4. **状态变量表**:全局量表、道具标记、解锁规则。
5. **节奏控制表**:每屏最短停留(起步值),阶段 6 实测回填。

> **逐行 vs 逐幕**:脚本表 = 玩家**说什么**;演出表 = 这一幕**怎么演**(镜头/交互/转场/钩子)。二者都要,别用一份顶两份 —— 只写台词会漏掉交互与转场,只写演出会不知道说什么。

> 上述结构常为目标项目的既有「场景/幕/段」数据结构的落点 —— 落库映射归该项目设计文档,勿在通用技能内写死。

### 台词权威只存一处(防漂移)

分镜/演出文档**严禁复制台词、选项文本与题量** —— 只写意图,冲突时**以数据文件为准**。抄一份 = 造第二事实源,改台词时必漏其一。文档头部写明权威文件是哪一份。

## 状态变量表(驱分支)

- **全局变量**:连续量表(例:信任值 Trust 0–100)、计数。
- **道具标记**:布尔(例:Has_Scroll 是否持有卷轴)。
- **解锁规则**:变量决定分支露出(例:信任 > 60 才现隐藏选项)。

守则:变量宁少勿多(少量全局 + 少量标记即可撑起好故事);每个变量必须**有读有写、有结局落点**,禁悬空;玩家侧要可感知(别设「看不见的进度条」)。表骨架见 `references/templates.md` §四。

## 节奏控制表

- 每屏最短停留:紧张 **2s** / 抒情 **5s**(起步值)。
- 实际停留时长在阶段 6 实测回填,反向修正本表 —— 别当固定真理。
- 骨架见 `references/templates.md` §五;情绪温度列供下游对接 `game-visual-design` 的情绪色盘。

## 存档与叙事状态的版本兼容(做连载 = 每次加章都在动别人的存档)

叙事状态(分支变量、道具标记、解锁进度)一旦落成存档,就与**内容版本**绑死。旧存档遇到新章节必须能升 —— 不能崩,也不能悄悄重置。

- **存档带 `schemaVersion`(整数)**:决定长期更新的游戏里最重要的一个字段。存的不是"进度",是"**哪一版规则下的进度**"。
- **读取管线恒为四步**:`读版本 → 逐版迁移 → 校验 → 实例化`。迁移**只增不改、不可重排**,每一版一个 `vN → vN+1` 纯函数并配单测(仓库侧对应:数字前缀迁移 + 只增列)。
- **未知 / 未来版本优雅降级**(返回空而非抛错):玩家回退到旧版本时,宁可提示"存档不兼容",不要崩。
- **内容 ID 迁移**:增删节点/场景时留一份 `removedId → replacementId` 映射;未知 ID **降级为占位并保留原 ID**,别静默丢弃玩家做过的事。
- **分层存**:稳定的**核心层**(身份、关键剧情节点、成就)与**逐版内容模块**分开;新章解锁**从旧选择推断**,而非重置进度让玩家重走。
- 写入用**原子替换**(临时文件 + rename):崩溃后只可能是旧存档或新存档,不会是半个。

> 一句话:**内容更新与存档兼容是同一问题的两面。** 只排结构不管存档 = 加一章崩一批老玩家。

## 逻辑校验闸门(写完即查,进视觉前)

| 检查 | 标准 |
| --- | --- |
| 不可达死胡同 | 每个分支末端都能到某个结局,无玩家走不到的死路 |
| 伪分支 | 选 A/B 不得同果(至少一处差异:文案/状态/结局) |
| 结局多样性 | **≥ 3 条截然不同的结局路径可达** |
| 结局覆盖率(开发末) | 每个预设结局均可被实际触发,防死循环 |

> 完整 6 项打勾清单与「结局覆盖率核对表」见 `references/templates.md` §六·§七 —— 进视觉前逐项打勾,别凭印象放行。

## 避坑

1. 分支膨胀:节点选项 2–4 个即可,宁可修剪;每多一层指数级成本。
2. 状态变量过多记不住:能合并就合并,别为「看起来复杂」加变量。
3. 文本密度硬线不豁免:超 30 字是砍句不是缩字(缩字仅 UI 保底)。
4. 视觉衔接:对白/呐喊的**气泡造型**落视觉 → 交 game-visual-design;选项点击/推进走目标项目**既有交互组件**,勿借叙事造引擎。
5. 偏离已锚定世界观的新点子 → 回阶段 0 重新锚定(见 game-pipeline 变更闸门),勿中途塞戏。

## 落到具体项目

本技能只含**通用结构方法**。叙事结构要落到某项目的 scene / choice / 存档数据字段时,**接缝与红线以该项目设计文档为准**(与代码漂移解耦,勿写死技能内)。

- **前置 →** `game-story-writing`:上游创作(圣经/角色/对白/伏笔)未定稿不排分支,否则返工。
- **交棒 →** `game-visual-design`:分支与演出表定稿后,气泡造型 / 镜头 / 立绘 prompt 归视觉侧。
- 本仓库(词库学习岛·千字谷):逐幕演出表 / 决策流 / 节奏表 → `docs/design/game-direction.md`。
- 结构落库的数据契约(字段名、读写点)写进**该项目的设计文档**;项目已有一套就并入,勿另起一份。
- 目标项目若无对应系统(如线性剧情无分支),**不虚构映射**;将来引入分支叙事须先走该项目立项流程,再建对应文档。
